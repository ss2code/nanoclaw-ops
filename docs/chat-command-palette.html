A compact command language for every NanoClaw container

A fleet-wide palette turns common instructions into short, deterministic chat commands while preserving provider-native commands, per-container skill isolation, destination access control, and NanoClaw’s message-only architecture.

The shared agent runner now owns one modular command surface. Every agent-group container gets the same parser, but help is personalized at runtime: it lists only skills actually mounted inside that container and only agent destinations that group is allowed to address.

Availability rule

The agent-runner source is mounted read-only into every container at /app/src, so no image rebuild or per-group installation is required for this source-only feature. A currently running process must restart (or naturally respawn) before it loads the new modules.

02

Architecture

ONE SMALL POLL-LOOP HOOK

The implementation deliberately avoids host routing and database schema changes. The poll loop invokes a runtime adapter; the adapter supplies live skills and destinations to a pure parser, then performs one of four outcomes.

container/agent-runner/src/ ├── chat-commands.ts # pure grammar, discovery, help, rewrites ├── chat-command-runtime.ts # DB response and agent delegation adapter ├── chat-commands.test.ts # unit + poll-loop integration coverage ├── poll-loop.ts # one palette hook ├── formatter.ts # recognize ACL-backed @agent follow-ups └── index.ts # pass provider/model context

Key implementation references: chat-commands.ts:1–12, chat-command-runtime.ts:50–108, poll-loop.ts:166–213, and formatter.ts:71–81.

03

Command grammar

COMPOSABLE LEFT TO RIGHT

The useful mental model is an envelope followed by an action. An optional agent address chooses the destination, an optional model tier chooses compute, and the remainder is either a skill, memory/task shorthand, or ordinary instruction.

message := [@agent] [/model hi|mid|low] action
action  := /enabled-skill [args]
         | /skill enabled-skill [args]
         | /run enabled-skill [args]
         | /recall query | /remember fact
         | /tasks [list|add|move|done|remove|sync] [args]
         | ordinary instruction
Model semantics

/model hi is explicit control, not a suggestion embedded in prose. It compiles to the existing [tier:high] directive consumed by Claude and OpenCode provider adapters. Aliases: high; mid, med, medium; lo, low; default, auto.

05

Skills and per-container visibility

DYNAMIC, NOT A GLOBAL CATALOG

The palette scans the current container’s skill root at command time. A child directory containing SKILL.md is directly invocable and appears in help. Instruction-only capability directories remain available to the agent but are not advertised as slash skills. Missing skills are hidden, and trying to invoke one returns a local error with /skills guidance.

Why this is safe

The host already selects and mounts group skills when spawning a container (src/container-runner.ts:397–462). The palette reports that mounted truth instead of inventing a second entitlement system.

06

Agent addressing

EXISTING MESSAGE PATH

@ag-xyz works when ag-xyz is the configured name of an agent destination visible to the source group. The source parser strips the address and writes the untouched remainder as an ordinary outbound agent message. The host’s existing agent-to-agent delivery path carries it to the target session, where that container resolves /model and skill availability against its own configuration.

  • Exact matches only: an unknown @name is left alone as an ordinary platform mention.
  • Access-controlled: /agents and routing use the same destination inventory.
  • Stream-safe: an ACL-backed @agent follow-up exits the active provider stream so the outer loop can route it.

User guide by example

COPY, ADAPT, SEND

Discover

/cmd-help
/cmd-help skills
/cmd-help memory-review
/skills
/agents
/status

Choose compute explicitly

/model hi diagnose the production delivery gap
/model mid summarize the latest research notes
/model low format these bullets as a checklist
/model show

Run skills

/memory-review --since 48h
/skill memory-audit evaluate consistency
/run daily-update
/model hi /memory-audit investigate stale entries

Only enabled skills succeed. /cmd-help <skill> shows the extracted description and all supported run forms.

Recall and remember

/recall what did we decide about provider switching?
/remember prefer preview deployments unless production is explicitly requested

These shorthands appear only when a memory capability is enabled. They compile to explicit agent instructions; the installed memory implementation remains responsible for retrieval, storage, policy, and confirmation.

Tasks

/tasks
/tasks list
/tasks add Review the migration report due Friday
/tasks move task-123 in-progress
/tasks done task-123
/tasks remove task-123
/tasks sync

The palette normalizes these into the central task contract already described to the agent. Removal must still follow the agent group’s confirmation policy.

Delegate and compose

@research /model hi investigate this regression
@trip-scotland /memory-review --since 48h
@writer /model low turn these notes into a concise update

Verification and rollout

EVIDENCE, NOT ASSUMPTION

Automated coverage

  • Dynamic skill discovery and descriptions.
  • All model aliases and model-plus-skill composition.
  • Three skill invocation forms and disabled-skill hiding.
  • Memory capability gating and task normalization.
  • ACL-backed agent routing and unknown platform mention pass-through.
  • JSON metadata and attachment preservation during rewrites.
  • End-to-end poll-loop delegation: two outbound messages, completed inbound, no source-provider query.
Passing checks

Complete agent-runner suite: 160 passed, 0 failed. Agent-runner TypeScript typecheck passed. Host TypeScript build passed.

Host suite environment limitation

The full host suite reached 875 passing tests but the existing scripts/q.test.ts subprocess checks failed because tsx could not create its local IPC pipe (listen EPERM …/tsx-…pipe). Vitest also reported file-watcher EMFILE errors. These are sandbox/resource failures outside the command-palette files, not patched as part of this feature.

Fleet rollout sequence

  1. Keep the updated shared agent-runner source in this repository; the host mounts it read-only at /app/src for every group.
  2. Restart any currently running agent-group containers. The host service itself needs no restart because no host runtime code changed.
  3. Containers load the new source on their next wake; no image or group config migration is needed.
  4. In any group, use /cmd-help to see that container’s real enabled skills and destinations.

Merge-resistance

Most behavior lives in two new modules and one new test file. Existing files have intentionally narrow changes: one poll-loop hook, one follow-up classification check, and provider context passed from the entrypoint. This reduces overlap with upstream lifecycle, router, and schema work.
