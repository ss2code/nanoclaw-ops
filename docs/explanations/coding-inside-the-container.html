Coding, Deploying & Iterating Inside the Container

Web-hosting models for NanoClaw

Written by Codex Research and architecture note · 19 June 2026

The clean mental model is: the web app is another NanoClaw messaging channel. It should not invoke the model container directly.

1. Vercel or Netlify

1.1 Where is the app built?

Both are possible, but they are separate concerns:

  • A NanoClaw agent can write the application inside its persistent group workspace, test it, push it to GitHub, or deploy it using the optional Vercel capability.
  • You can instead build it interactively using Codex or Claude on the host.
  • In the usual production workflow, the coding agent pushes a branch or PR, then Vercel or Netlify performs the actual deployment build from Git. Vercel describes Git-triggered preview and production deployments as its standard workflow. Vercel Git deployments

So the NanoClaw container is the developer, not part of the deployed web application. Once deployed, the app runs on Vercel or Netlify independently.

Direct vercel deploy from inside an agent container is supported by this installation's optional add-vercel capability. I would use that for prototypes; for important applications I prefer:

agent branch → PR → preview deployment → human approval → main → production

1.2 Can the hosted app call a local agent group?

Yes, but not directly through NAT. NanoClaw v2 currently has no generic public “call agent” REST endpoint.

There are three sensible patterns:

  1. Cloud broker/queue — my recommendation.

    The browser writes messages to a small authenticated cloud API and queue. A host-side NanoClaw ChannelAdapter polls that queue, passes messages through the normal router, and posts replies back.

    This matches NanoClaw's architecture: adapters provide onInbound() and deliver() in src/channels/adapter.ts, while the router applies permissions, creates the correct session, writes inbound.db, and wakes the container in src/router.ts.

    The Mac initiates every network connection, so no inbound firewall or public port is needed. It also survives browser disconnects and agent responses that take several minutes.

  2. Tunnel directly to a host web adapter.

    Run the web UI/API on the NanoClaw host and expose that one port through Cloudflare Tunnel or Tailscale.

    Cloudflare Tunnel uses outbound-only connections from the local machine while allowing bidirectional HTTP traffic. Cloudflare Tunnel documentation

    For private personal access, Tailscale Serve is especially attractive. Tailscale Funnel makes it public, whereas Serve limits access to devices and users in your tailnet. Tailscale Serve · Tailscale Funnel

  3. Move the complete NanoClaw host to an always-on VPS.

    Then the web adapter, central DB, session DBs, and agent containers all live on the cloud VM. This is the simplest genuinely public or multi-user architecture, but it is a VPS/container-host model—not Vercel Functions or Netlify Functions.

A purely static Vercel page cannot reliably reach a sleeping Mac. It needs either a backend queue or a tunnel.

Is Vercel or Netlify an anti-pattern?

Hosting the frontend and a thin relay there is perfectly reasonable.

Hosting the NanoClaw daemon itself in their serverless functions is the anti-pattern. NanoClaw expects:

  • An always-running host process.
  • Persistent SQLite databases and workspace files.
  • Docker or Apple container management.
  • Long-lived polling and delivery loops.

Vercel Functions scale to zero, have maximum execution durations, and expose only a temporary writable filesystem. Vercel function lifecycle · Runtime filesystem and streaming limits Netlify Background Functions similarly stop after 15 minutes. Netlify Background Functions

Use a VM, dedicated container host, or home Mac for NanoClaw itself.

2. Locally hosted web app

2.1 Can it run inside the agent container?

Technically yes, but it is the wrong place for the durable chat interface.

An agent container is:

  • Created per NanoClaw session.
  • Allowed to stop when idle.
  • Potentially replaced or restarted.
  • Deliberately prevented from owning host-side routing.
  • Only one side of the two-database protocol.

A dev server inside the container is useful while building and visually testing an app. It should not become NanoClaw's permanent ingress server.

A separate, ordinary long-running Docker container could host the UI, but it would still need a defined bridge to the NanoClaw host. It should never write inbound.db directly or invoke the agent runner directly.

2.2 Does it have to run on the host?

The integration endpoint should run in, or immediately beside, the host process.

The actual frontend assets can be anywhere:

  • Served by the NanoClaw host.
  • Served by a separate local process or container.
  • Hosted statically on Vercel.
  • Hosted behind Tailscale or Cloudflare.

But a host-side ChannelAdapter should remain the authority that maps authenticated web users to NanoClaw users, messaging groups, agent groups, and sessions. NanoClaw already has a host webhook server seam in src/webhook-server.ts, although it is currently designed for installed channel adapters rather than a generic agent API.

What implementations online currently do

The pattern I found most often is:

  • A local or self-hosted web server owns the UI and WebSocket connection.
  • That server connects to the local agent or model backend.
  • Remote access is added through a reverse proxy, mesh VPN, or tunnel.

For example, the third-party NanoClaw Web UI runs an Express/WebSocket server locally and defaults to localhost for security. Important caveat: its documented compatibility is NanoClaw v1.x, so it is architectural evidence, not something I would install into this v2 checkout unchanged.

My recommendation for this installation

Start with a host-side v2 web channel:

  1. Local Node web server/channel adapter.
  2. Browser authentication mapped to NanoClaw users.
  3. Messages enter only through onInbound().
  4. Replies leave only through deliver().
  5. Access privately with Tailscale Serve.

If you later need a public web application, keep the frontend on Vercel and add a small durable cloud queue. The same host adapter can switch from local WebSocket ingress to polling that queue without changing the agent groups.

What is actually doing the coding

The thing writing code is an agent — Claude, driven by the Claude Agent SDK — running headless inside a per-session container. The host spawns it (src/container-runner.ts), the entrypoint launches the agent-runner on Bun (container/agent-runner/src/index.ts), and that runner polls the session database and calls the model in a loop. The agent has the normal toolset — Bash, Read, Edit, Write, Task (subagents) — and its working directory is /workspace/agent (container/agent-runner/src/index.ts:40). So "coding inside the container" is literally the agent editing files and running commands there, the same as Claude Code does on your laptop.

The image ships a real toolchain (container/Dockerfile): Node 22, Bun, pnpm, git, headless Chromium (for visual verification via agent-browser), and pinned CLIs — claude-code, agent-browser, vercel. Two things differ from coding on the host: network egress is proxied through the OneCLI gateway so real credentials never enter the container (src/container-runner.ts:430), and the container is disposable (--rm) — all durable state lives in the mounts, not the container.

Host vs container — who runs what (and the two "web servers")

The single line to keep straight: there are two processes with two different jobs. The host is the always-on Node process on your Mac — the switchboard. The container is a per-session, --rm sandbox — the workshop where the agent actually runs code. When earlier sections say "into the container," the message in fact lands at the host first, which then wakes the container.

AspectHost — switchboardContainer — workshop
RunsRouting, channel adapters, delivery, the chat web server you talk throughThe agent — its Bash/Edit/Write/Read tools; writes & runs code; builds, tests, deploys
NetworkReceives messages; serves the chat UI on a port (e.g. 3080)Egress-only (proxied); no inbound ports published
LifecycleRuns continuouslySpawned on demand; dies when idle
IO to the otherWrites inbound.dbReads inbound.db, writes outbound.db

The chat web server is host-side for a principled reason, not convention: it sits upstream of session selection — it decides which container a message routes to, so it can't live inside any one container.

The two different "web servers"

Most of the confusion comes from "web server" meaning two unrelated things:

  • The chat-channel server — the UI you send messages to the agent through (the "web channel" / nanoclaw-web-ui). Host-side. Plumbing.
  • A web app the agent builds for you — a Next.js app, an API, a landing page. The agent writes and runs this inside the container, then deploys it out to the cloud (Vercel/Netlify). The product.

Different layers: the first is how you reach the agent; the second is the agent's work output.

So what is Docker actually for?

The container is the sandbox where AI-generated code executes — that is its whole value:

  • It's where the agent does its labor. Every git clone, pnpm build, test run, headless-browser screenshot, and vercel deploy happens in the container. The host never runs agent code — you don't want an AI executing arbitrary shell commands in your trusted orchestrator.
  • Isolation / security — arbitrary code runs in a throwaway Linux box, not on your Mac; secrets never enter it (OneCLI proxy).
  • Reproducible toolchain — pinned Node / Bun / pnpm / Chromium / vercel every spawn.
  • Your source still lands on your disk — the working dir is a bind mount, so the code persists in groups/<folder>/ even though the container is disposable. Docker is the workbench, not the deploy target.

Does a web server ever run inside the container?

Yes — but only the agent's own dev/test server, transiently. While building an app the agent will run pnpm dev (say on container-localhost :3000), point its headless Chromium at it, screenshot, and iterate. That is a real web server inside the container — but bound to the container's own localhost, not exposed to your Mac, and gone when the container exits. It exists for the agent's verify loop. The container is not a durable or public host (egress-locked, ephemeral, per-session), so anything you or others connect to long-term is deployed out to the cloud — which is exactly why the Vercel/Netlify path exists.

Can you iterate & see the files? Yes — but the control surface differs

You are not blind. Your group folder lives on your Mac at groups/<folder>/ and is bind-mounted into the container at /workspace/agent (src/container-runner.ts:272). Every file the agent creates lands on your disk in real time — a real group folder already holds package.json, node_modules, scripts/, docs/, working files. You can open it in your editor, git diff it, watch it change.

The real difference is how you drive it: local Claude Code is a synchronous cockpit you fly from a terminal; the container agent is an asynchronous autopilot you supervise over chat. You lose the live tool-by-tool stream and the shared shell; you gain always-on, run-from-your-phone autonomy — with the files still on your disk for out-of-band inspection and editing.

The loop you talk through

On the left you type and watch every step. On the right your chat message becomes a row in inbound.db (src/router.ts), the agent-runner wakes, does its work, and writes the reply into outbound.db; the host's delivery poll sends it back to you (src/delivery.ts). You steer by sending the next message — not by Ctrl-C.

Where the files live

The group folder and the session DBs are host directories mounted read-write into the container. The container is ephemeral; the mounts are not. That is why you can review the agent's work in your own tools, and why a human-in-the-loop git flow is possible — it is the same .git directory on disk.

Use cases, pros & cons

What fits this model (chat-triggered, always-on, isolated): build-and-deploy-me-a-small-web-app or landing-page deliverables; data scraping → processing → an HTML report; automating a recurring workflow (e.g. Trip Companion, Ops Center); scheduled or unattended jobs; long autonomous runs you kick off from your phone and check later; anything where you want OS isolation (throwaway container) plus credential isolation (the OneCLI vault).

DimensionProsCons
ReachAlways-on, reachable from anywhere via chatChat is a lossy steering surface for complex code
IsolationArbitrary code runs in a --rm container; secrets never enter itContainer logs are ephemeral — fine-grained debugging is harder

The git interface — who decides commit & push

No magic: it is plain git in the container, with auth solved for you. The image ships git; outbound HTTPS to github.com / api.github.com gets the real token injected by the OneCLI proxy (container/skills/onecli-gateway/instructions.md), so git clone and git push over HTTPS work without any token ever living in the container.

You decide when to commit and push — via chat, exactly like telling local Claude Code "commit and push." Or you delegate it inside a task ("when tests pass, commit to a branch and open a PR"). Nothing is automated unless you ask. Where the repo lives — three patterns:

  1. In the group folder — /workspace/agent equals groups/<folder>/ on your Mac. The agent commits in-container and you review the diff and push from your own tools. Same repo, two hands on it — the cleanest human-in-the-loop story.
  2. A remote GitHub repo the agent clones into the workspace, works on, and pushes back — good for an existing project.
  3. PR flow — with the GitHub credential it can gh pr create or use the API: work a branch → push → open a PR → you review on GitHub and merge.

So: bring your own git discipline; NanoClaw removes the credential friction and lets you keep the review/merge gate yourself.

How web apps get built & deployed

Two container skills cover this. frontend-engineer enforces a build → visually-verify-in-Chromium → deploy discipline and forbids declaring "done" without a screenshot (container/skills/frontend-engineer/SKILL.md). vercel-cli handles shipping (container/skills/vercel-cli/SKILL.md):

vercel deploy --yes --prod --token placeholder

The --token placeholder is the OneCLI pattern again — the proxy swaps in your real Vercel token (matched to api.vercel.com) at request time. The /add-vercel host skill is what installs the vercel CLI into the image and wires that injection.

Netlify isn't shipped as a skill, but the pattern is identical: add netlify-cli to the group's container config (install_packages), register a Netlify token in the OneCLI vault keyed to api.netlify.com, and run netlify deploy. Nothing in the architecture is Vercel-specific — Vercel just has a pre-built skill.

Can a Vercel/Netlify web app be a channel into a local agent group?

Yes — once you understand the direction of the connection. A "channel" is a host-side adapter (src/channels/adapter.ts): it calls onInbound(...) when a message arrives and implements deliver(...) for replies. It runs in the host Node process on your Mac, not in the container.

The catch: your host is local, behind NAT — no public inbound IP. The reply path is never a problem (the host makes an outbound call). Inbound is the only hard part. The clean, NAT-friendly answer is to have the host poll the cloud — exactly how the Telegram adapter already works. Your web app becomes "your own Telegram."

Pattern A — host polls a thin backend

The web app needs a small backend with a queue (a serverless function + KV / Upstash / Supabase). The browser talks to that backend; your channel adapter long-polls it for new messages and POSTs replies back. The host initiates every connection, so NAT is a non-issue.

The alternative (Pattern B) is to expose the host's webhook server (src/webhook-server.ts, 0.0.0.0:3000) via an ngrok/cloudflared tunnel so the cloud can POST in. It works, but adds a tunnel dependency and a public attack surface. Pattern A is cleaner. A purely static site with no backend can't be a reliable channel — there is nowhere to queue a message between polls.

Net: the web app can absolutely be a chat channel into your local agent group, and the architecture is ready for it — you'd write a roughly one-file host-side ChannelAdapter that polls your web app's backend. What you can't do is have a static cloud page "reach into" a local host with no relay; the queue in the middle does the NAT traversal for you.

What actually exists today (verified 2026-06)

This isn't only theory — a browser channel has been built for NanoClaw several times, and one detail matters: in every real version the chat UI is served by the host process (a port like 3080), not by the container. The host serves the page and injects each message into inbound.db; the container is only woken to run the agent. The official repo has had the same "web channel — browser portal" proposed at least three times — #819, #1298, and #1863 (by VivianBalakrishnan, commit ee2dafc) — but all are closed/unmerged, so it is not in trunk; the docs list it as a planned future skill. The usable off-the-shelf option is the standalone WhosClaw/nanoclaw-web-ui (WebSocket + POST /api/send). No Vercel/Netlify-hosted variant (Pattern A above) has been published — everyone who shipped this serves the UI from the host instead.

Reaching it remotely — and why a tunnel doesn't capture your other traffic

Because the UI lives on the host, "remote access" just means letting your browser reach that one host port:

  • Same network (home Wi-Fi) — no tunnel. Bind the server to 0.0.0.0 and open http://<mac-lan-ip>:3080 from any device on the LAN.
  • Away — one inbound hole through NAT via an ingress tunnel (Cloudflare Tunnel / ngrok) or a private mesh (Tailscale). Either exposes only port 3080.

An ingress tunnel publishes one local port inbound; it is the opposite of a full-tunnel VPN and never reroutes your general browsing. Three independent traffic paths make this concrete:

TrafficPathOn the tunnel?
Your normal browsingStraight out your device's normal connectionnever
The chat channelBrowser → the host's port → inbound.db → containeronly this
The agent's own net accessOut the container's egress via the OneCLI proxyseparate

Tailscale is the cleanest personal option. Install it on the phone and the Mac, and reach the server at http://<mac-tailnet-ip>:3080 from anywhere — no public URL, encrypted, device-ACL'd. It is split-tunnel by default: only traffic addressed to your tailnet devices uses the mesh; all other phone traffic goes out normally. The one setting that would route everything through the Mac is selecting it as an exit node — don't, and you get exactly the "just this web server" behavior you want.

The "built it overnight" stories — reconciled with iterative dev

The framework you're thinking of is almost certainly OpenClaw (NanoClaw's open sibling), not "OpenCloud" — but the overnight phenomenon is general across Claude Code, OpenHands/Devin, and others. The thing to digest:

"One-shot overnight" is one-shot for the human, not for the machine. You give one well-specified prompt at night; by morning there's a working app. Under the hood the agent ran a highly iterative loop — generate → run → observe failure → fix → repeat — often hundreds of cycles. The iteration didn't disappear; it got automated and moved off your clock. Your iterative workflow is the same loop — the only question is whether you sit in each cycle or the agent self-drives against an automatic "done" check.

What makes it converge

A machine-checkable definition of done. Claude Code's creator Boris Cherny's one unbroken rule: always give the agent a way to verify its own work — tests that must pass, a type-check, a build that must succeed, a screenshot it compares to the spec. The popular "Ralph Wiggum" loop wraps this in a script with a completion promise: a stop-hook re-runs the agent until that phrase appears, so it neither quits early nor loops forever.

Where it works: greenfield, well-specified, verifiable (a CRUD app, a landing page, scaffolding, a feature with tests). Where it breaks: ambiguous specs, design taste, and the "last 30%" — edge cases, security, production polish. That's the widely-cited 70% problem: AI gets you 70% fast, the final 30% still needs you. Overnight builds are real, but they hand you a strong working draft, not always production-final.

Small distilled examples of how people run it

  1. Spec-file + loop (Ralph) — write a PRD/checklist in markdown ("these routes, these tests pass, deploy to Vercel"); a loop makes the agent pick the next unchecked item → implement → run tests → commit → repeat. Wake up to a stack of commits.
  2. PRD-driven greenfield (Devin/OpenHands) — "Build a web app for X." The agent decomposes, scaffolds Next.js, runs it in a sandbox, browses the page, fixes runtime errors, opens a GitHub PR you review in the morning.
  3. Issue-queue grinder — point it at a backlog of GitHub issues; it works them one at a time, each as its own PR (one documented run: 182 PRs / 206 issues over 10 days).
  4. Tests-first — you write the tests (that's the spec), the agent loops until green. TDD with the agent as implementer; the suite is the "done."

Takeaway for someone who builds iteratively: you're not doing it wrong. The overnight crowd just (a) front-loads a tight spec, (b) hands the agent an automatic verifier, and (c) lets it iterate unattended. For ambiguous, high-taste work, human-in-the-loop iteration still wins. NanoClaw's container makes the overnight pattern possible — bash, a headless browser, deploy, and scheduling — but it doesn't change that fundamental tradeoff.

Glossary

agent-runner
The TypeScript program (on Bun) inside the container that polls the session DB and calls the model in a loop.
bind mount
A host directory exposed inside the container at a path; edits on either side are the same files on disk.
ChannelAdapter
Host-side code that feeds inbound platform messages to the router and delivers the agent's replies back.
completion promise
A sentinel phrase an autonomous loop must emit to signal genuine "done", checked by a stop-hook.
group folder
groups/<folder>/ on the host — the agent's persistent workspace, mounted at /workspace/agent.
OneCLI gateway
An outbound HTTPS proxy that injects real credentials per request, so secrets never enter the container.
Ralph Wiggum loop
An overnight technique: re-run the agent against a task list with a verifier until the completion promise appears.
session DB
Per-session SQLite split into inbound.db (host writes) and outbound.db (container writes) — the sole IO surface.
70% problem
AI reaches ~70% of a working app fast; the last 30% (edge cases, security, polish) still needs a human.
