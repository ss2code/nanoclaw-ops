Runtime Grounding Events

Every inbound turn, including follow-ups, the agent-runner can read the group's durable memory and optional domain SQLite state, inject a read-only snapshot into the model's prompt, and write an audit row recording that it did so. The mechanism is generic; Trip Companion is one consumer.

What it is & why it exists

The generic memory source of truth is memory.db in the group workspace. A domain skill may add a source such as trip.db for structured state — roster, families, decisions, or scratchpad — but a domain DB is optional. A warm session can drift from these files, and a tool search that returns nothing can be mistaken for "there is nothing stored." Both failure modes lead to stale or empty assumptions.

Grounding closes that gap. Before each turn reaches the model, buildGrounding() reads memory.db and any optional domain DB read-only, then prepends the compatibility <trip_grounding> block. The block carries the current snapshot and says that "a zero-result search is not proof that the memory database is empty"; unreadable data must be reported as a grounding failure, not a clean slate.

A grounding event is the durable audit trail of that act: a row in grounding_events capturing what was injected, whether the reads succeeded, whether the user asked to remember something, and — after the turn — whether the active-memory count actually grew. That last signal is what lets the Ops Center catch an agent that said it saved something but didn't.

Architecture & role

Four small functions in container/agent-runner/src/trip-grounding.ts — now named buildGrounding, recordGrounding, prependGrounding, and finalizeGrounding — run around the provider query. The producer writes grounding_events into the session's outbound.db (the container is its sole writer); the host-side Ops Center is the consumer, reading those rows back as health evidence.

The diagrams below retain historical trip-named labels because archived traces and compatibility aliases still use them. For the current generic contract, see the canonical memory reference.

The design is deliberately read-only on the source DBs and append-only on the audit table. Grounding never mutates trip.db or memory.db — it only observes them. The agent itself does the writing (via the trip-memory CLI when a remember is requested); grounding just measures the before/after, so the audit can't lie about what the agent did.

How the snapshot is built

Applicability gate

Grounding only applies when trip.db or memory.db exists in the workspace (trip-grounding.ts:167). For a generic, non-trip group neither file is present, so the snapshot is marked applicable: false, the prompt is left untouched, and no event is recorded — grounding is a no-op everywhere except Trip Companion sessions.

Remember detection

requestsRemember() (trip-grounding.ts:143) scans the inbound text for triggers like "remember…", "note that…", "keep in mind…" while explicitly excluding negations like "don't remember." When matched, the prompt gains an instruction to persist via trip-memory and return the save receipt; the recorded event flags remember_requested = 1.

Turn lifecycle

The poll loop drives all four functions around a single provider query. The same dance runs for follow-up messages pushed mid-stream — each follow-up batch gets its own grounding event, finalized when the query stream closes.

The crucial ordering: memory_count_before is captured at record time (turn start) and memory_count_after at finalize time (turn end). If a remember was requested, remember_satisfied is set true only when the active count strictly increased (trip-grounding.ts:241). No remember requested → remember_satisfied stays null.

Data structures

grounding_events table (outbound.db)

Schema at container/agent-runner/src/db/connection.ts:110. One row per grounding act.

CREATE TABLE grounding_events (
  id                  INTEGER PRIMARY KEY AUTOINCREMENT,
  created_at          TEXT NOT NULL,   -- record time (turn start)
  completed_at        TEXT,            -- finalize time (turn end); NULL if turn died
  message_ids_json    TEXT NOT NULL,   -- which inbound messages this turn grounded
  core_ok             INTEGER NOT NULL,-- trip.db read succeeded?
  memory_ok           INTEGER NOT NULL,-- memory.db read succeeded?
  core_summary_json   TEXT NOT NULL,   -- snapshot of trip/members/decisions/scratchpad
  memory_summary_json TEXT NOT NULL,   -- counts + owner + matched/profile rows
  errors_json         TEXT NOT NULL,   -- any read errors (drives "snapshot failed" warnings)
  remember_requested  INTEGER NOT NULL DEFAULT 0,
  remember_satisfied  INTEGER,         -- 1 / 0 / NULL(=not requested)
  memory_count_before INTEGER NOT NULL DEFAULT 0,
  memory_count_after  INTEGER          -- NULL until finalize
);

TripGroundingSnapshot (in-memory)

Returned by buildGrounding(). The transient object that feeds both the prompt and the recorded row. The old TripGroundingSnapshot name remains a compatibility alias.

interface TripGroundingSnapshot {
  applicable: boolean;          // false outside Trip Companion -> grounding is a no-op
  coreOk: boolean;              // trip.db read ok
  memoryOk: boolean;            // memory.db read ok
  coreSummary: Record<string, unknown>;        // optional domain summary
  memorySummary: {                              // total/active/pending/rejected counts
    total: number; active: number; pending: number; rejected: number;
    owner: string | null; rows: MemoryRow[];    // lexical matches or active-profile fallback
  };
  errors: string[];
  rememberRequested: boolean;
  prompt: string;               // the <trip_grounding> block prepended to the model prompt
}

End-to-end: a "remember" turn

  1. Message lands — user says "remember the villa check-in is 3pm"; the poll loop pulls the pending batch (poll-loop.ts:227).
  2. Build — buildGrounding(cwd, keep) reads memory.db and any optional domain DB, sees the remember trigger, and composes a prompt block whose memory summary includes matched or profile rows.
  3. Record — recordGrounding() INSERTs the row with remember_requested = 1 and returns groundingEventId.
  4. Prepend & query — the grounding block is glued in front of the formatted messages and handed to the provider (poll-loop.ts:229–236).
  5. Agent acts — guided by the prompt, the agent saves the fact via the generic memory CLI and returns the save receipt; memory.db now has one more active row.
  6. Finalize — in the poll loop's completion path, finalizeGrounding() re-reads memory and resolves remember_satisfied when the active count increased.
  7. Audit — the Ops Center later reads this row; because the count grew, no warning fires. Had the agent skipped the save, remember_satisfied would be 0 and the dashboard would flag it.

Why it matters: the Ops Center consumer

readGrounding() in ops-center/readers/trips.ts:197 reads the most recent 30 events per session and the newest 50 overall, then readTripCompanions() turns the latest event into operator warnings (ops-center/readers/trips.ts:261):

Condition on latest eventWarning raisedMeans
no events at allno runner grounding evidence yetThe runner has never grounded this group — either brand new or grounding isn't running.
!coreOk || !memoryOklatest grounding snapshot failedA source DB was missing/unreadable; the agent answered without authoritative state.
rememberRequested && rememberSatisfied === falseexplicit remember request produced no new active memoryThe user asked to remember something and nothing was persisted — a silent memory bug.

This is the payoff of recording before/after counts rather than trusting the agent's narration: the dashboard can assert "a save was promised and a save did not happen," grounded in the database, not in chat text.

Notes & gotchas

  • Follow-ups are grounded too. Messages pushed into an already-active query get their own build/record/prepend at poll-loop.ts:411–414, collected in followupGroundingIds and finalized when the stream closes (poll-loop.ts:498). A long multi-message turn produces several events.
  • A dead turn leaves completed_at = NULL. If the container crashes mid-turn, the row is recorded but never finalized — which is itself a useful signal (recorded-but-not-completed = the turn didn't finish cleanly).
  • The XML block is marked authoritative="true". It is deliberately positioned to outrank the agent's own recollection; the wording about zero-result searches is load-bearing anti-hallucination text, not boilerplate (trip-grounding.ts:185–195).
  • Two identical schemas. The table is created both in the forward-compat CREATE TABLE IF NOT EXISTS path (connection.ts:110) and the fresh-DB path (connection.ts:266); keep them in sync when altering columns.
  • Read-only, best-effort reads. Source DBs are opened read-only; read failures are captured into errors_json rather than thrown, so missing or unreadable state degrades to a recorded failure instead of crashing the turn.

Glossary

grounding
The per-turn act of injecting authoritative live DB state into the model's prompt before it answers.
grounding event
A row in grounding_events recording one grounding act and its before/after outcome.
core
The structured trip state read from trip.db: trip row, active members, families, open decisions, open scratchpad items.
memory
Durable user-requested facts in memory.db, classified by status (active / pending / rejected).
remember trigger
Inbound text that requestsRemember() classifies as an explicit request to persist a fact.
remember_satisfied
Whether a requested remember actually increased the active-memory count: 1 yes, 0 no, NULL not requested.
applicable
Whether the workspace has memory.db or an optional domain DB; false makes grounding a no-op.
