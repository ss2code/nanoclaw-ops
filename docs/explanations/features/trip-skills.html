How the container runs the trip-* skills

A feature trace of the Trip Companion stack: how five skills get mounted into a per-group agent container, how the agent discovers and fires them, and how the functionality is actually implemented — deterministic Bun CLIs over SQLite, with the LLM only ever parsing language, never doing the math.

The big idea

The five trip skills — trip-core, trip-finance, trip-planning, trip-docs, and trip-workflows — live in container/skills/. They are not code the host imports. They are mounted read-only into the agent container, and the agent reaches them in two ways: a small set of always-on rules baked into CLAUDE.md, and the rest discovered on demand through the SDK's Skill tool when an incoming message matches a skill's description. Durable memory is the generic memory skill, not a trip-specific storage engine.

Source layout update (2026-07-05): the canonical source for all six trip skills (the five above, plus trip-workflows) now lives one level deeper, under container/skills/trip-companion-skills/<skill>/. The old top-level paths — container/skills/trip-core/, container/skills/trip-docs/, etc. — are kept as symlinks into that directory purely for backward compatibility with persisted group configs and composed instructions, so every path in this document still resolves. New reads/edits should go to the trip-companion-skills/ copy; see its README.md for the portability contract.

Every skill follows the same shape: a SKILL.md (the playbook the LLM reads), a Bun CLI dispatcher in scripts/<name>.ts, and a SQLite data layer in scripts/db.ts. The agent never mutates state itself — it parses natural language (and images) into CLI commands, runs them with the Bash tool, and relays what the script computed. That single rule — "you judge, the script computes" — is what makes the numbers, the lifecycle, and the vote tallies trustworthy.

One more layer sits underneath the skills: the agent-runner performs generic per-turn grounding. Before every turn, including follow-ups, it reads memory.db and any optional domain DB such as trip.db, then prepends an authoritative snapshot. See the canonical memory reference for the distinction between this read-only first pass and model-issued memory CLI recall.

Two ways a skill reaches the agent

At every container spawn, buildMounts() (src/container-runner.ts:243) runs two host-side steps that wire the skills up. Both read from the same source tree, container/skills/, which is itself mounted read-only at /app/skills (src/container-runner.ts:319). For the trip skills specifically, the entries under container/skills/ are compatibility symlinks into the consolidated trip-companion-skills/ tree (see the note above); the mount and everything downstream is unaffected because it resolves through the symlink.

Must-fire vs on-demand

Must-fire: a skill that ships an instructions.md gets it symlinked into the group's .claude-fragments/ and @imported by the composed CLAUDE.md (src/claude-md-compose.ts:64). Because the agent's working directory is /workspace/agent (container/agent-runner/src/index.ts:40) and that is where the composed CLAUDE.md is mounted, these rules load every turn. Only trip-memory and trip-docs use this — their behaviours (always recall before suggesting; always keep one canonical doc) can't wait to be "discovered".

On-demand: syncSkillSymlinks() (src/container-runner.ts:343) drops a symlink per selected skill into /home/node/.claude/skills/ pointing at /app/skills/<name>. The SDK is started with settingSources: ['project','user','local'] (container/agent-runner/src/providers/claude.ts:418), so it indexes those skills and surfaces each one's name + description. When a message matches, the model fires the allowlisted Skill tool (claude.ts:60) and the full SKILL.md body loads into context.

A turn in motion

You judge, the script computes

When a money message arrives, the agent matches trip-finance's description and loads it. It resolves names through the roster ($TF members — aliases included), plays back what it understood when anything was inferred, and only then commits with $TF log. The script returns the exact per-person shares, which the agent echoes. The agent never adds up a balance itself — a wrong amount is the one unacceptable failure, so arithmetic is delegated entirely to the tested CLI.

The same loop powers the other skills: trip-core owns the legal stage-transition table and the deterministic vote tally; trip-planning owns the completeness gate and feasibility checks. The LLM's job is interpretation and judgement; the script's job is state and math.

The implementation pattern: a CLI per skill

Each skill's functionality is a Bun command-line program the agent invokes through Bash. The entrypoint is a thin argument parser plus one big dispatch switch keyed on "<group> <verb>" — see main() in container/skills/trip-companion-skills/trip-core/scripts/trip-core.ts:131. Sub-scripts (lifecycle.ts, decisions.ts, participation.ts, …) hold the actual logic; db.ts owns the schema.

# Every skill is invoked the same way — a tested CLI over the group's SQLite file.
TC="bun /app/skills/trip-core/scripts/trip-core.ts --db /workspace/agent/trip.db"
TF="bun /app/skills/trip-finance/scripts/trip-finance.ts --db /workspace/agent/trip.db"
TP="bun /app/skills/trip-planning/scripts/trip-planning.ts --db /workspace/agent/trip.db"

$TC recap                 # rebuild full trip state (stage, roster, decisions, notes)
$TF log --desc "Lunch" --amount 4500 --currency INR --payer 5 --rule by-family --by 2
$TP plan validate         # the readiness gate: completeness + feasibility

Two properties make this robust. First, output is dual-mode: human-readable text by default, structured JSON with --json (used by tests and the host-side simulator). Second, every state mutation is wrapped with a row in the append-only journal table (appendJournal(), trip-core/scripts/db.ts:174), so every change is attributable and edits are reversible.

The part that isn't a skill: runner-side grounding

Skills tell the agent it should read state first. The agent-runner makes sure it does. Before every turn, including follow-ups, the poll loop calls generic buildGrounding(cwd, messages), which reads memory.db and any optional domain DB such as trip.db read-only and assembles an authoritative compatibility XML snapshot — matched memory rows or an active-profile fallback plus any domain state — then prepends it to the prompt.

It also does light verification. If the inbound message contains a "remember" trigger, the snapshot instructs the agent to persist it via the generic memory CLI and show the save receipt. A grounding_events row is written before the turn (recordGrounding) and reconciled after (finalizeGrounding) — comparing memory counts to confirm the "remember" was actually honoured. The automatic pass is read-only and is not the same as an observable, reinforcing model-issued memory recall. The snapshot is tagged authoritative="true" and explicitly warns the agent that a zero-result search is not proof the store is empty. See the canonical memory reference.

Where state lives

One file, layered migrations

trip-core owns the shared tables and creates them with migrateCore() (trip-core/scripts/db.ts:33): trip, families, members, relationships, stage_participation, decisions, scratchpad, assets, journal. The feature skills layer their own tables into the same trip.db: trip-finance adds expenses/expense_shares/settlements via migrateFinance() (trip-finance/scripts/db.ts:21) and re-exports the core helpers; trip-planning adds the plan model via migratePlanning() (trip-planning/scripts/db.ts:26). Each openDb() runs openCoreDb() first, then its own migrate — idempotent CREATE TABLE IF NOT EXISTS.

trip-memory is deliberately separate: memory.db (openMemoryDb(), trip-memory/scripts/db.ts:9) holds the curated, approval-gated long-term store with an FTS5 index — Tier-2 memory that may lag, kept apart from the ungated working state in trip.db.

All trip databases use PRAGMA journal_mode = DELETE, not WAL. The group directory is a bind mount, and WAL sidecar files don't propagate reliably across the mount boundary — the host-side simulator and tests read these files while the container writes them, so DELETE mode is load-bearing for cross-mount visibility. Money is stored in integer minor units; balances are reported per-currency and never silently converted.

trip-docs: HTML master → delivered PDF

trip-docs keeps the canonical document as styled HTML in /workspace/agent and delivers a rendered PDF, never the HTML itself. renderToPdf() (container/skills/trip-companion-skills/trip-docs/scripts/render.ts:66) resolves a headless Chromium binary (resolveChromium(), preferring the container's baked-in /usr/bin/chromium), runs it with --headless=new --print-to-pdf (buildPdfArgs(), render.ts:49), and polls until the output file size settles before reaping the process — headless Chrome tends to linger instead of exiting. It refuses to overwrite the HTML master and throws an actionable error if no Chromium is found, so the agent never claims a PDF it didn't produce. Page geometry comes from the document's own @page/print CSS, keeping renders deterministic.

End-to-end: a message becomes durable state

  1. Host spawns the container — spawnContainer() (src/container-runner.ts:109) materializes container.json, mounts the group dir at /workspace/agent and container/skills at /app/skills.
  2. Skills are wired — syncSkillSymlinks() creates the per-skill symlinks; composeGroupClaudeMd() rebuilds CLAUDE.md with the always-on instructions.md imports.
  3. Runner grounds the turn — the poll loop reads pending messages, builds the generic <trip_grounding> compatibility snapshot from memory.db and optional domain state, and prepends it to the prompt.
  4. Agent interprets — matches the message to a skill description, fires Skill(<name>) (or already has the must-fire rules in context), and parses language/images into a CLI command.
  5. Script computes & persists — the agent runs the CLI via Bash; the script mutates trip.db/memory.db, writes a journal row, and prints the exact result.
  6. Agent confirms or delivers — it echoes the script's computed result (shares, tally, version), and for documents renders a PDF and attaches it.
  7. Runner reconciles — finalizeGrounding() records whether a "remember" request appears to have increased active memory; the response is written to outbound.db for the host to deliver.

Key design decisions & gotchas

  1. The LLM never does math or owns state charter rule

    Every SKILL.md repeats "you judge, the script computes." Balances, vote tallies, legal stage transitions, and completeness gates are computed by tested CLIs, not inferred. This is why a wrong-but-confident number is treated as the one unacceptable failure — the architecture removes the opportunity for it.

  2. Two load surfaces, chosen by cost composition design

    Behaviours that must apply on every turn (recall-before-suggest, one-canonical-doc) ship an instructions.md and live in CLAUDE.md. Everything else is description-triggered through the Skill tool, costing zero tokens until needed. Adding instructions.md to a skill is the one switch that flips it to always-on.

  3. One trip.db, layered migrations db design

    trip-core owns the shared schema; finance and planning layer their tables into the same file and re-export core helpers. This keeps the roster single-sourced and lets a cross-cutting query (or the grounding snapshot) read everything from one handle. Curated memory is split out into memory.db precisely because it has different durability semantics.

  4. journal_mode = DELETE is mandatory cross-mount constraint

    The group dir is a bind mount and the host reads these DBs while the container writes them. WAL sidecar files don't cross that boundary reliably, so all trip DBs run in DELETE mode. Switching to WAL would silently break the host-side simulator and tests.

  5. Grounding is enforced by the runner, not trusted to the model reliability

    Rather than hope the agent reads the recap, the runner injects an authoritative snapshot every turn and audits whether "remember" requests were honoured. The automatic pass is read-only; precise model-issued recall remains the observable/reinforcing retrieval path. The agent is told a zero-result search is not proof of an empty store.

Glossary

always-on / must-fire
A skill behaviour loaded into CLAUDE.md every turn via an instructions.md fragment.
dispatcher
The scripts/<skill>.ts entrypoint: an arg parser plus a switch that routes <group> <verb> to logic.
grounding snapshot
The authoritative compatibility <trip_grounding> XML the runner prepends to each prompt, summarizing live memory and optional domain state.
journal
The append-only audit table in trip.db; every mutation records before/after JSON and the actor.
layered migration
A feature skill calling openCoreDb() then its own migrate* to add tables to the shared trip.db.
minor units
Money stored as integers (e.g. paise/cents) so arithmetic is exact and rounding is explicit.
recap
trip-core's read-back of full trip state; the agent is told to run it first, and the runner grounds with the same data.
SKILL.md
The skill playbook the LLM reads; its frontmatter description is what triggers on-demand loading.
