Trip Lifecycle Expansion Pack — Implementation Spec

Spec date: 2026-07-10 · Target: container/skills/trip-companion-skills/ in the NanoClaw repo · Hard dependency: the Improvement Pack (docs/trip-suite-improvement-pack.html) §1 ensureColumn and §2 heartbeat must exist. If they don't, implement those two sections first, exactly per that spec.

The existing suite covers planning, deciding, and money. This pack covers the rest of a group vacation's life: preparation (packing, shared gear, T-minus readiness), travel day (concierge card, roll-call), on-trip living (stay/safety cards), memories (diary, photo indexing, the recap document), and closure (settlement drive, preference distillation). Seven features, each with schema, CLI, behavior, instruction edits, and tests — implementable in one pass.

§0 Ground rules

All conventions from the Improvement Pack §0 apply verbatim: bun:sqlite with $name params, journal_mode=DELETE untouched, money in integer minor units via trip-finance/scripts/money.ts, ISO strings compared lexicographically, every mutation journaled via appendJournal, additive-only migrations (IF NOT EXISTS + ensureColumn), bun:test only, no new npm deps, no host-side (src/) changes, model judges / scripts compute. Acceptance gate:

Heartbeat extension points. Several features below add sections to the heartbeat JSON. Implement each as an optional section producer in trip-core/scripts/heartbeat.ts: a function (db, atIso) => sectionValue | null registered per edition. Sections that return null are omitted; a non-empty new section counts toward wakeAgent under the same rules as the base sections. Keep each producer's queries in this pack's owning module and import it from heartbeat.ts (same cross-skill relative-import pattern finance/planning already use).

§1 Checklists engine: packing, shared gear, readiness trip-core

Why: the classic group failure — three speakers, zero first-aid kits, and someone who never did online check-in. One small engine covers all three list shapes.

1.1 Schema (add to migrateCore)

CREATE TABLE IF NOT EXISTS checklists (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  kind TEXT NOT NULL,            -- 'packing' | 'gear' | 'readiness'
  title TEXT NOT NULL,
  created_at TEXT NOT NULL,
  created_by INTEGER REFERENCES members(id)
);

CREATE TABLE IF NOT EXISTS checklist_items (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  checklist_id INTEGER NOT NULL REFERENCES checklists(id),
  label TEXT NOT NULL,
  due_date TEXT,                 -- readiness items: absolute ISO date
  per_member INTEGER NOT NULL DEFAULT 0,   -- 1 = each member confirms individually
  claimed_by INTEGER REFERENCES members(id),  -- gear: who's bringing it
  status TEXT NOT NULL DEFAULT 'open',     -- open | done | dropped
  note TEXT,
  created_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS checklist_confirmations (
  item_id INTEGER NOT NULL REFERENCES checklist_items(id),
  member_id INTEGER NOT NULL REFERENCES members(id),
  at TEXT NOT NULL,
  PRIMARY KEY (item_id, member_id)
);

1.2 CLI (new module trip-core/scripts/checklists.ts, cases in the dispatcher)

$TC gear add --label "Bluetooth speaker" [--note …] --by <id>
$TC gear claim <itemId> --member <id>         # exit 1 if already claimed by someone else
$TC gear unclaim <itemId> --member <id>       # only the claimer (or --force) may unclaim
$TC gear board                                 # unclaimed first, then claimed w/ names
$TC packing seed --template beach|hill|city --by <id>   # idempotent by label
$TC packing add --label "Snorkel gear" [--per-member] --by <id>
$TC packing board
$TC readiness seed --by <id>                   # T-minus items from trip.start_date (below)
$TC readiness confirm <itemId> --member <id>   # per_member items: one row per member
$TC readiness done <itemId> --by <id>          # group-level items
$TC readiness due [--at <ISO>]                 # due/overdue items + per-member gaps
$TC check drop <itemId> --by <id>              # any list: status → dropped

Behavior rules:

  • One checklist row per kind, auto-created on first use (kind='gear', title "Shared gear", etc.). All writes journaled (checklist.claim, checklist.confirm, …) with actor.
  • Gear claim races: claim is a compare-and-set (UPDATE … SET claimed_by=$m WHERE id=$i AND claimed_by IS NULL); if zero rows changed, exit 1 and report the current claimer.
  • Packing templates are static data in code (a TEMPLATES map in checklists.ts: beach/hill/city × ~12 sensible items each; every template includes the shared first-aid kit as a gear item, not packing). Seeding twice adds nothing (dedupe by exact label). Plan-derived extras ("snorkel gear because Tuesday's item is snorkeling") are the agent's judgment via packing add — never inferred by the script.
  • Readiness seed creates from trip.start_date (exit 1 if unset), all per_member=0 unless noted:
    OffsetLabelper_member
    T-7Book airport transfers / cabs0
    T-3Confirm ID documents valid & packed1
    T-2Share meds / allergy notes if any1
    T-1Online check-in1
    T-1Download offline maps for destination(s)0
    Re-seed after a start-date change: readiness seed updates due_dates of its own seeded items (match by label) instead of duplicating.
  • readiness due --at: items with due_date ≤ at and not done; for per_member=1 items, list which active on-trip participants (participation status not 'out' for start_trip) haven't confirmed.

1.3 Heartbeat sections

  • planning edition (only when stage is plan_ready or within 7 days of start_date): readinessDue = output of the due query; gearUnclaimed = unclaimed gear items when within 3 days of start.

1.4 Instruction edits

trip-core/SKILL.md, new section "Packing, gear & readiness" (place after Assets): the command block above plus: "When the plan locks (plan_ready), offer once to seed packing (pick the template from the trip's destinations), seed readiness, and start the shared-gear board. Claiming is first-come: relay claim conflicts as-is. When the heartbeat lists readiness gaps, @mention only the members who haven't confirmed, once, politely." Add one line to instructions.md: "Packing/gear/readiness state lives in trip.db via $TC gear|packing|readiness … — never track it in prose."

1.5 Tests — new file trip-core/test/checklists.test.ts

  1. Gear: add → claim → second claim by another member exits 1 naming claimer; unclaim by non-claimer exits 1, --force works; board orders unclaimed first.
  2. Packing: seed beach twice → no duplicates; per-member item confirm tracked per member.
  3. Readiness: seed with start 2026-08-14 → due_dates 08-07/08-11/08-12/08-13/08-13; due --at 2026-08-12 returns exactly the T-7/T-3/T-2 items; per-member gaps exclude an 'out' participant and a confirmed member; re-seed after date change updates dues without duplicating.
  4. Heartbeat: within-3-days trip with unclaimed gear → gearUnclaimed present and wakes; 10 days out → absent.
  5. All mutations journaled with actor.

§2 Stay cards, safety cards, day-of concierge trip-planning + trip-core

Why: "what's the wifi", "what's the address for the driver", "where's the nearest pharmacy", "which terminal am I" are the highest-frequency on-trip questions, all answerable from state captured once.

2.1 Schema (add to migratePlanning)

CREATE TABLE IF NOT EXISTS place_info (
  place_id INTEGER NOT NULL REFERENCES places(id),
  key TEXT NOT NULL,             -- free-form; conventional keys below
  value TEXT NOT NULL,
  source_url TEXT,
  updated_by INTEGER REFERENCES members(id),
  updated_at TEXT NOT NULL,
  PRIMARY KEY (place_id, key)
);

Conventional keys (document in SKILL.md, not enforced): stays → wifi, door_code, host_phone, checkout_time, house_rules, address_local (address in local script for taxi drivers). Destinations → emergency, hospital, pharmacy, police, embassy.

2.2 CLI (extend places.ts + dispatcher)

$TP info set --place <id> --key wifi --value "GoaVilla / sunset2026" [--source-url …] --by <id>
$TP info unset --place <id> --key wifi --by <id>
$TP stay card [--stay <id>]        # default: the committed stay covering date(now)
$TP safety card [--destination <id>]  # default: committed destination for date(now)
  • stay card renders one text block: stay place name, address + address_local, map_url, check-in/out dates, checkout_time, then every info key/value, then a "missing" line listing conventional keys not yet set (that gap list is what prompts the agent to collect them at check-in).
  • safety card: destination place + its info rows in the emergency/hospital/pharmacy/police/embassy order, same missing-gaps line. Upsert semantics on info set (REPLACE into the PK), journaled.
  • "Committed stay covering date(now)": check_in ≤ date < check_out, status committed; none → exit 1 "no committed stay covers <date> — pass --stay".

2.3 Day-of concierge (trip-core, because it joins roster + legs + stays)

$TC dayof [--member <id>] [--date <YYYY-MM-DD>]   # default: all members, today

Per member with a committed leg on that date: one block — name, each leg (mode carrier depart→arrive, ref, booking_url), then the night's stay place + address + host_phone. Members with no legs that day are omitted; if nobody has legs and no stay changes, print "no travel today". Read-only, no journal.

2.4 Heartbeat + instructions

  • Morning edition: when any committed leg departs today, add section dayof = the concierge data (reuse the module).
  • trip-planning/SKILL.md new section "On-trip cards": commands + "At each check-in, collect wifi/door/host/checkout once via info set and confirm what you stored; answer 'wifi?/address?/rules?' with stay card, and 'pharmacy/hospital/emergency' with safety card. Fill safety keys at planning time from verified sources (store the URL in --source-url). Never answer these from chat memory."

2.5 Tests — new file trip-planning/test/cards.test.ts (+ dayof cases in trip-core/test/cli.test.ts)

  1. info set upserts (set twice → one row, latest value) and journals; unset removes.
  2. stay card auto-picks the stay covering the injected date; boundary: on check_out date it does NOT match (lexicographic <); missing-keys line lists exactly the unset conventional keys; no covering stay → exit 1.
  3. safety card ordering + gaps.
  4. dayof: member with 2 legs today renders both in depart order + stay block; member without legs omitted; no-travel day → the quiet message.

§3 Roll-call trip-core

Why: "is everyone at the gate?" — message-driven presence, no location tracking (deliberately: privacy + battery + it fits the everything-is-a-message architecture).

3.1 Schema + CLI

CREATE TABLE IF NOT EXISTS rollcalls (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  label TEXT NOT NULL,
  opened_by INTEGER REFERENCES members(id),
  opened_at TEXT NOT NULL,
  closed_at TEXT
);
CREATE TABLE IF NOT EXISTS rollcall_checkins (
  rollcall_id INTEGER NOT NULL REFERENCES rollcalls(id),
  member_id INTEGER NOT NULL REFERENCES members(id),
  at TEXT NOT NULL,
  note TEXT,
  PRIMARY KEY (rollcall_id, member_id)
);
$TC rollcall open --label "Airport T2" --by <id>    # exit 1 if one is already open
$TC rollcall in --member <id> [--note "at security"]  # against the open rollcall
$TC rollcall status                                  # in ✅ / missing ⬜ vs on-trip roster
$TC rollcall close --by <id>
  • Expected set = active members whose on_trip participation isn't 'out'. Duplicate check-in updates the note/time, doesn't error. Only one open roll-call at a time (simplicity; enforced). All open/close journaled.
  • Instructions (trip-core/SKILL.md, one paragraph under a new "Roll-call" heading): "'Everyone here?' / 'roll call at the cab' → open one, mark people in as they say so ('here', '2 min away' → in with note), answer status from the script. Sender ≠ target still applies ('Maya's with me' marks Maya). Close it when complete and say so."

3.2 Tests — extend trip-core/test/cli.test.ts or new rollcall.test.ts

  1. Open→in→status shows correct missing set (excludes 'out' participant); double open exits 1; duplicate in updates note; close then in → exit 1; full check-in → status reports complete.

§4 Trip diary & photo indexing trip-core

Why: memories are the artifact people keep, and capture must be zero-effort. Two pieces: a one-line-per-evening diary, and day/place tags on the existing asset index so photos land somewhere findable.

4.1 Schema + CLI

CREATE TABLE IF NOT EXISTS diary_entries (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  date TEXT NOT NULL,
  member_id INTEGER REFERENCES members(id),   -- NULL = group entry
  entry TEXT NOT NULL,
  created_at TEXT NOT NULL
);
-- assets: day/place tagging
ensureColumn(db, 'assets', 'day_date', 'day_date TEXT');
ensureColumn(db, 'assets', 'place_id', 'place_id INTEGER');
$TC diary add --date 2026-08-15 --entry "Sunset cruise — dolphins!" [--member <id>] --by <id>
$TC diary show [--date …]            # all entries, grouped by date
$TC asset index … [--day 2026-08-15] [--place <placeId>]   # extend existing command
$TC asset list [--day …] [--place …]                        # extend existing filters

Multiple entries per member per date allowed (they're moments, not slots). Journaled as diary.add.

4.2 Heartbeat + instructions

  • Evening edition: section diaryPrompt = {hasEntryToday: boolean} — lets the agent end the digest with one light question ("highlight of today?") only when nobody has answered yet. Never nag twice.
  • trip-core/SKILL.md, extend the Assets section: "On-trip, when a photo lands with an @mention, index it with --day (message date) and --place when known from today's plan. When someone answers the evening highlight question — or says anything diary-shaped ('best part of today was…') — save it with diary add and confirm in a word, not a ceremony."

4.3 Tests — new file trip-core/test/diary.test.ts

  1. Add/show grouped by date; member vs group entries; asset day/place filters; heartbeat diaryPrompt.hasEntryToday flips after an entry; ensureColumn idempotency on a legacy assets table.

§5 The recap document trip-docs

Why: the payoff artifact — the scrapbook the group forwards for years — and by trip end every input already sits in trip.db. This is a new composed doc type alongside master.

5.1 Scope + CLI

$TD new goa-recap --title "Goa 2026 — The Recap" --type recap
$TD compose goa-recap --db trip.db     # regenerates generated regions, preserves prose blocks
$TD bump / show / render               # unchanged machinery

--type recap scaffolds the same versioned shell as master (version markers, revision history, references, print CSS) with these generated regions (hash-guarded exactly like master's — reuse the existing generated-region mechanism in compose.ts; do not fork it) and prose blocks blocks/<slug>/{intro,highlights,outtakes}.html:

RegionSource
Route stripReuse the existing schematic SVG generator (committed destinations, nights, hop modes).
Trip statsDeterministic: nights away, destinations count, committed items done, Σ committed travel_minutes ("~X h on the move"), photos indexed, diary entries. Money: per-currency active-expense totals + top 3 expenses (via finance modules) — totals only, never balances/debts (a recap is not a bill).
Day-by-dayPer committed day: theme + committed items (titles only) + that date's diary entries + up to 6 photo assets for the date as <img> with relative paths (assets live under /workspace/agent/assets/…, the doc lives in /workspace/agent/ — relative paths keep the PDF render working).
SuperlativesClosed decisions whose question starts with [superlative] — question (prefix stripped) + outcome. The agent runs the end-of-trip awards as normal trip-core polls titled that way (instructions below); zero closed superlatives → region renders a friendly placeholder.

5.2 Instruction edits

trip-docs/SKILL.md, new short section "The recap": "When the trip completes (stage trip_complete/post_trip), offer once to build the recap: run 2–3 fun superlative polls first (decision open --question "[superlative] Trip MVP?" --mode poll …), then new --type recap, write the intro/highlights prose from the diary, compose, render, send the PDF. It's a keepsake: warm tone, no balances, no logistics." Add the recap row to the what-goes-where table.

5.3 Tests — extend trip-docs/test/compose.test.ts (follow existing seeding pattern)

  1. Scaffold: new --type recap creates shell v1 + the three prose block stubs.
  2. Compose from a seeded trip.db (2 destinations, 3 days, diary entries, day-tagged photo assets, 1 closed [superlative] poll, expenses incl. voided): stats numbers exact (voided excluded); day cards contain diary text + ≤6 imgs with relative src; superlative rendered with prefix stripped; no balance/debt strings anywhere in output.
  3. Prose blocks survive recompose; hand-edit inside a generated region → compose refuses (same behavior as master); empty trip.db → compose succeeds with placeholders, exit 0.
  4. bump/show behave identically to master docs (one canonical file).

§6 Settlement drive trip-finance + heartbeat

Why: the lifecycle already models post_trip; the heartbeat's settlement edition (Improvement Pack §2) already reports balances every 3 days. This section adds the two small pieces that make it a drive: reminder state (so nudges escalate honestly and stop) and the archive handshake.

6.1 Schema + CLI

CREATE TABLE IF NOT EXISTS settlement_nudges (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  at TEXT NOT NULL,
  edges_json TEXT NOT NULL      -- the outstanding edges at nudge time
);
$TF nudge record [--at <ISO>]   # heartbeat/agent records that a reminder went out
$TF nudge status                # count, last nudge time, whether edges changed since
  • Heartbeat settlement edition gains fields: nudgeCount, lastNudgeAt, edgesChangedSinceLastNudge (compare current edges to the last recorded edges_json, order-normalized). Wake rule tightens: outstanding balances wake only if edgesChangedSinceLastNudge or ≥3 days since lastNudgeAt (never spam a static debt daily).
  • Instructions (trip-finance/SKILL.md, "Settling the trip" section): "In post-trip, when the heartbeat wakes you with balances: send the settle plan with --links, then $TF nudge record. Escalate tone gently with nudgeCount (1: friendly plan · 2: direct @mentions of who owes · 3+: suggest the group settle it face-to-face and offer to stop reminding). When allSettled, celebrate briefly and propose stage confirm --to archived to the owner."

6.2 Tests — new file trip-finance/test/nudge.test.ts

  1. Record/status roundtrip; edgesChangedSinceLastNudge false for identical edges (regardless of edge order), true after a new settlement partially clears one edge.
  2. Heartbeat: fresh debt → wake; nudge recorded, same edges, +1 day → no wake; +3 days → wake; edges changed next day → wake; all settled → final wake with allSettled.

§7 Preference distillation at trip close trip-memory — instructions only

Why: the person-level export/import (Improvement Pack §8) is the plumbing; this is the moment that fills it. No new code — one instruction flow, plus a single heartbeat flag.

  • Heartbeat settlement edition: add distillPending: true until a memory tagged distilled exists for the trip (query the memory store; if the memory DB is absent, omit the flag — never error).
  • trip-memory/SKILL.md, new section "After the trip": "Once home, run one distillation pass with the owner: propose 3–5 candidate durable preferences you observed but never saved ('early starts were misery for half the group', 'the standout day was the unplanned one') — each as a normal remember the owner then approves/forgets, plus one memory tagged distilled marking the pass done. Then offer the export for returning travellers' next trip."
  • Tests (extend trip-memory/test/cli.test.ts): a memory tagged distilled flips the heartbeat flag off (test via the heartbeat producer directly with a seeded memory.db path); absent memory.db → flag omitted, no crash.

§9 Implementation record (2026-07-10)

This pack is implemented in the Trip Companion skill suite. The implementation keeps the specified boundary: all changes are inside container/skills/trip-companion-skills/; no host-side code, dependencies, currency conversion, payment execution, or location tracking was added.

  • Core lifecycle state: additive core migrations now provide checklist, confirmation, roll-call, diary, and asset day/place metadata. ensureColumn is the shared idempotent additive-column helper.
  • Checklists: checklists.ts implements static beach/hill/city templates, idempotent seeding, readiness due dates derived from trip.start_date, participant gaps, and compare-and-set shared-gear claims. Every mutation writes the journal.
  • Cards and travel day: planning’s place_info table and cards cover stay facts and safety facts; core’s dayof joins committed legs and the nightly stay.
  • On-trip capture: roll-call is message-based only; diary entries and indexed photos are queryable by date and place.
  • Heartbeat: heartbeat.ts supplies deterministic JSON for planning, morning, evening, and settlement editions, including readiness, gear, concierge, diary, nudge, and optional memory-distillation sections. It has the extension-producer registration point required by this pack.
  • Recap: --type recap creates a versioned shell with hash-guarded generated regions and authored intro, highlights, and outtakes blocks. Compose draws its route, stats, committed-day diary/photo cards, and [superlative] results from trip.db, deliberately excluding balances/debts.
  • Settlement and memory closure: normalized transfer edges are persisted with each nudge so static debt is not re-notified daily; an optional existing memory.db is inspected for the distilled tag without creating or failing on a missing memory database.

Focused regression coverage was added for checklist idempotency/claims/readiness gaps, roll-call and diary/photo filtering, stay/safety cards, settlement-edge change detection, and recap composition. The complete six-suite acceptance gate passed after the change.

§10 User guide examples

The assistant-facing skills now contain these command flows too. These examples show what a new Trip Companion user can ask for and the corresponding deterministic state action.

Before the trip: packing, gear, and readiness

User: "We are going to Goa — make a packing list."
Assistant: choose the relevant template and seed it once.
$TC packing seed --template beach --by 1

User: "Add snorkel gear for everybody."
$TC packing add --label "Snorkel gear" --per-member --by 1

User: "I will bring the Bluetooth speaker."
$TC gear claim 7 --member 2

User: "What are we still late on?"
$TC readiness due

User: "My online check-in is done."
$TC readiness confirm 12 --member 2

Gear claims are intentionally first-come. If somebody already claimed an item, the assistant reports the stored claimant rather than guessing or overwriting it.

At the stay: one reliable answer for recurring questions

User: "The villa Wi-Fi is GoaVilla / sunset2026; checkout is 11."
$TP info set --place 5 --key wifi --value "GoaVilla / sunset2026" --by 1
$TP info set --place 5 --key checkout_time --value "11:00" --by 1

User: "What is the Wi-Fi and taxi address?"
$TP stay card

User: "Where is the nearest pharmacy?"
$TP safety card

At check-in, the card calls out missing conventional values (door code, host phone, local taxi address, and so on) so facts are captured once, verified, and then read back from state.

Travel day and meeting up

User: "Give us the travel-day brief for tomorrow."
$TC dayof --date 2026-08-15

User: "Open a roll call for Airport T2."
$TC rollcall open --label "Airport T2" --by 1

User: "Maya and I are through security."
$TC rollcall in --member 3 --note "through security with Alice" --by 1

User: "Who are we waiting for?"
$TC rollcall status

User: "Everyone is here."
$TC rollcall close --by 1

Roll-call tracks voluntary message check-ins only; it never uses GPS or background location.

During the trip: preserve the little moments

User: "Best part today was the dolphin sunset cruise."
$TC diary add --date 2026-08-15 --entry "Dolphin sunset cruise" --member 2 --by 2

User sends a photo at Chapora Fort.
$TC asset index --kind photo --label "Chapora Fort sunset" \
  --path assets/photos/chapora-sunset.jpg --day 2026-08-15 --place 9 --by 2

User: "Show our August 15 memories."
$TC diary show --date 2026-08-15
$TC asset list --day 2026-08-15

After the trip: settle gracefully and close the loop

User: "Who still needs to settle?"
$TF settle
$TF nudge status

Assistant sends the agreed reminder, then records it:
$TF nudge record

User: "What did we learn for our next trip?"
$TM remember --trip goa-2026 --title "Relaxed mornings" \
  --content "Avoid early starts for this group" --category preference \
  --tags distilled --importance 4 --by "Trip owner"

The nudge state prevents daily repetition when nothing has changed. The distilled tag marks that the owner-led preference pass is complete.

Create and share the recap

User: "Make a scrapbook of the Goa trip."

# Optional fun awards first
$TC decision open --question "[superlative] Trip MVP?" \
  --mode poll --options "Maya|The sunset cruise|Chapora Fort" --by 1

# Create the one canonical keepsake and its authored prose stubs
$TD new goa-recap --title "Goa 2026 — The Recap" --type recap

# Write warm prose in blocks/goa-recap/intro.html, highlights.html, outtakes.html,
# then regenerate state-derived regions and produce the shareable artifact.
$TD compose goa-recap --db /workspace/agent/trip.db
$TD render goa-recap

The recap is a warm artifact: it includes route, day cards, diary moments, photos, trip totals, and awards. It never includes balances, debts, or a payment demand.
