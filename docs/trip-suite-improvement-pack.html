Trip Suite Improvement Pack — Implementation Spec

Spec date: 2026-07-10 · Target: container/skills/trip-companion-skills/ in the NanoClaw repo · Companion doc: docs/trip-lifecycle-expansion-pack.html (implement THIS pack first — the other depends on §2 and §1 here).

This document specifies eight improvements to the existing Trip Companion skill suite, in implementation order. Each section gives the schema change (exact DDL), the CLI surface (exact commands and output contracts), behavior rules, the instruction-file edits, and the tests to write. It is written to be implemented in one pass, tests included, with no further design decisions needed.

§0 Ground rules — read before writing any code

Repo layout and conventions (verified against the tree as of 2026-07-10)

  • Canonical source: container/skills/trip-companion-skills/<skill>/. Each skill has SKILL.md (on-demand instructions), instructions.md (always-on rules composed into the agent's CLAUDE.md), scripts/<skill>.ts (CLI dispatcher) plus per-module scripts, and test/*.test.ts.
  • Runtime aliases: containers invoke /app/skills/trip-<name>/scripts/…. The aliases at container/skills/trip-* point into this suite — new commands are automatically available through them. Do not rename or move any existing path.
  • The model judges, scripts compute. Every new behavior that involves state, counting, money, dates, or eligibility must live in the script. Instruction text only tells the agent when to call which command and how to relay results.
  • All trip state lives in one SQLite file per group: trip.db (core + planning + finance tables layered by each skill's migrate* step). Memory lives in a separate memory.db.

Hard technical constraints

  • bun:sqlite, not better-sqlite3. Named params must use $name in both SQL and the JS object: .run({ $id: id }). Positional ? also fine.
  • PRAGMA journal_mode = DELETE is load-bearing (bind-mount visibility). Never change pragmas; always open DBs through the existing helpers (openCoreDb / openPlanningDb / finance openDb).
  • Money is integer minor units in the DB; CLI flags take major units. Use the existing helpers in trip-finance/scripts/money.ts (formatMinor, and the existing major→minor parse used by log --amount). Never introduce floats into stored amounts.
  • Dates/times are ISO-8601 strings compared lexicographically (existing convention, see activeParticipants in trip-core/scripts/db.ts).
  • Every mutation is journaled with appendJournal(db, {at, actorId, action, entity, before, after}) from trip-core/scripts/db.ts. Follow the entity/action naming already used (e.g. decision.objection).
  • Tests use bun:test (never vitest — vitest cannot load bun:sqlite). Follow the style in the existing test/ dirs: create a temp DB per test via the open helpers, inject time with an explicit --at/now argument, no reliance on wall-clock.
  • No new npm dependencies. No changes to package.json, bun.lock, the Dockerfile, or anything under src/ (host). This pack is entirely inside the skills tree.
  • Existing schema is created with CREATE TABLE IF NOT EXISTS and live groups already have populated trip.db files. All schema changes must be additive and idempotent — new tables via IF NOT EXISTS, new columns via the ensureColumn helper (§1). Never rewrite or drop a table.

How to verify (the acceptance gate)

bun test container/skills/trip-companion-skills/trip-core
bun test container/skills/trip-companion-skills/trip-planning
bun test container/skills/trip-companion-skills/trip-finance
bun test container/skills/trip-companion-skills/trip-memory
bun test container/skills/trip-companion-skills/trip-docs
bun test container/skills/trip-companion-skills/trip-workflows

All suites must pass, including every pre-existing test (the finance golden/characterization/property tests are the regression canary — if they fail you broke split math). There is no separate tsc gate for the skills tree; bun test is the gate. Live containers pick up script changes on their next restart; no image rebuild is needed for skill files.

Do not: add npm deps · touch generated-region hashing in trip-docs · change pragmas · do arithmetic in instruction text · break the finance golden tests · store major units · use Date.now() anywhere a test needs determinism (thread a now/--at parameter instead, defaulting to current time at the dispatcher edge only).

§1 Shared helper: ensureColumn trip-core

Several features below add columns to existing tables. Add one helper to trip-core/scripts/db.ts and use it everywhere; both packs share it.

/** Additive, idempotent column migration. `ddl` is the full column def, e.g. "upi_id TEXT". */
export function ensureColumn(db: Database, table: string, column: string, ddl: string): void {
  const cols = db.query(`PRAGMA table_info(${table})`).all() as { name: string }[];
  if (!cols.some((c) => c.name === column)) {
    db.exec(`ALTER TABLE ${table} ADD COLUMN ${ddl}`);
  }
}

Call sites live inside each skill's own migrate step (migrateCore / migratePlanning / migrateFinance) so any entry point that opens the DB heals the schema. New columns must default to NULL (SQLite ALTER limitation) — code must treat NULL as "feature not configured".

Tests (trip-core/test/core.test.ts, add cases): calling ensureColumn twice is a no-op; column exists after migrate on a DB created from the old DDL (simulate by creating the table without the column first).

§2 Trip heartbeat trip-core — the keystone feature

Why: every capability in the suite is pull-based. trip.db is full of time-shaped state (decision commit_by, ticket_deadline, trip dates) that nobody sweeps. NanoClaw's container agents already have a schedule_task MCP tool whose optional pre-task script hook runs bash first and only wakes the agent when the script prints {"wakeAgent": true, "data": …} (see container/agent-runner/src/mcp-tools/scheduling.instructions.md). The heartbeat is a deterministic CLI command shaped exactly for that contract.

2.1 New file trip-core/scripts/heartbeat.ts + dispatcher case

trip-core heartbeat [--at <ISO>] [--edition morning|evening|auto]
  • --at defaults to the current time at the dispatcher edge; everything below receives it as a parameter (testability).
  • --edition auto (default) resolves by stage: pre-trip stages → planning checks; start_trip/on_trip → morning; post_trip → settlement. Explicit morning/evening force the on-trip editions.
  • Output is always JSON on stdout, exactly one line-delimited object, matching the schedule-script contract:
{
  "wakeAgent": boolean,
  "data": {
    "stage": "planning" | … ,
    "edition": "planning" | "morning" | "evening" | "settlement",
    "at": "<the --at echo>",
    "sections": { … only non-empty sections present … }
  }
}

2.3 wakeAgent rule

  • planning: wake iff at least one section is non-empty.
  • morning: always wake while stage is start_trip/on_trip (the daily brief is the product), including the todayGap case.
  • evening: wake iff spendToday.count > 0 or tomorrow has a committed day or gap while on-trip.
  • settlement: wake iff there are outstanding balances, or iff all-settled and stage is still post_trip (one final wake proposing archive).
  • Stages archived / cancelled / trip_complete-with-nothing-due: {"wakeAgent": false, "data": {…}}. Never throw on an empty or unconfigured trip — print wakeAgent:false with data.reason.

2.5 Tests — new file trip-core/test/heartbeat.test.ts

  1. Unconfigured DB → wakeAgent:false, has data.reason, exit code 0.
  2. Planning stage, one propose decision past commit_by without objection → appears in decisionsDue; with an objection logged → absent; future commit_by → absent.
  3. Poll with 3 eligible members, 1 voted, 1 marked out for the stage → pendingVoters lists exactly the 1 remaining.
  4. Deadline at --at+3d → in deadlinesSoon; +10d → absent; −1d → absent (it's a feasibility error, not a heartbeat item).
  5. All sections empty → wakeAgent:false.
  6. On-trip morning with a committed day (2 items, ordered by slot) → today.items in slot order; no committed day → todayGap:true and still wakeAgent:true.
  7. Evening: two expenses logged "today" at --at, one voided → count 1, correct per-currency totals; zero expenses and no tomorrow day → wakeAgent:false.
  8. Post-trip with a known 3-member ledger → transfer edges match settle's plan exactly (import and compare, don't re-implement); fully settled → allSettled:true.
  9. Archived stage → wakeAgent:false for every edition.
  10. Determinism: same DB + same --at → byte-identical JSON.

§3 Feasibility upgrades trip-planning

Why: feasibility.ts checks only intra-day slack, night coverage, budget cap, and passed deadlines. Three real-world failure modes are unguarded: arriving at a closed attraction, destination handoffs with no transport, and days that exceed the group's pace.

3.1 Opening hours

  • Schema: ensureColumn(db, 'places', 'open_hours', 'open_hours TEXT') in migratePlanning. Format v1: a single daily range string "HH:MM-HH:MM" (e.g. "09:00-17:00"). Anything unparseable is ignored with a warning (never an error).
  • CLI: add place set --id <n> [--open-hours "09:00-17:00"] [--name …] [--map-url …] to places.ts (a general field-setter; journal the change as place.set).
  • Check (in checkPlan): for every committed itinerary item with a place_id whose place has parseable open_hours, and which has start and/or end times: start before open or end after close → error "«title» is outside «place» hours (09:00-17:00)". Item has the place but no times → warning "«title»: place has opening hours but item is untimed".

3.2 Destination handoffs

For each consecutive pair of committed destinations (by order_index) that both have committed stays: let out = previous stay's check_out, in = next stay's check_in. Rules (all warnings — data is often thin here and warnings never block):

  • No committed transport_hops row connecting the two destinations' places (either direction of from_place_id/to_place_id matching the stays' places) → "no committed transport between «A» and «B» (checkout 2026-08-17)".
  • A connecting hop exists but its depart date ≠ check_out date → "hop departs 2026-08-18 but «A» checkout is 2026-08-17".
  • check_out date > check_in date of the next stay (overlap/impossible order) → warning naming both.

3.3 Pace cap

  • Schema: ensureColumn(db, 'trip', 'pace_cap_minutes', 'pace_cap_minutes INTEGER').
  • CLI: trip-planning config set-pace --minutes 300 --by <id> (journaled; --minutes 0 clears it → NULL). Also print it in plan show's header when set.
  • Check: per committed day, load = Σ travel_minutes of committed items + Σ (end−start) for items with both times. If cap set and load > cap → warning "day 2026-08-15 load ≈ 6h20m exceeds pace cap 5h".
  • Bridge from memory (instruction, not code) — append to trip-planning/instructions.md: "When trip-memory holds a pace/mobility preference (e.g. 'walks ≤ 5km', 'no packed days'), translate it once into a deterministic cap via $TP config set-pace and tell the group what you set. Feasibility then protects it automatically; never eyeball pace yourself."

3.4 Tests — extend trip-planning/test/feasibility.test.ts

  1. Committed item 18:00–19:00 at a place open 09:00–17:00 → 1 error; 10:00–11:00 → clean; malformed open_hours "9ish-late" → no error, one warning at most, never throws.
  2. Untimed committed item at a place with hours → warning.
  3. Two committed destinations w/ stays and no hop → handoff warning; add committed hop on the checkout date → clean; hop dated +1 day → date-mismatch warning; overlapping stays → order warning.
  4. Pace: cap 300, day with 200m travel + 90m timed activity → clean; +150m more travel → warning; no cap set → never warns; candidate (non-committed) items excluded from load.
  5. Regression: existing four checks still pass untouched (run whole suite).
  6. plan validate still blocks on errors and passes with only warnings (extend validate.test.ts with one opening-hours error case).

§4 Rain alternates & day shuffle trip-planning

Why: on-trip replanning ("it's pouring", "we're 2h behind") is where deterministic recomputation beats improvisation. Two pieces: stored alternates, and a transactional dry-run shuffle.

4.1 Schema + CLI

  • ensureColumn(db, 'itinerary_items', 'alternate_for_item_id', 'alternate_for_item_id INTEGER').
  • item add … --alternate-for <itemId>: validates the target exists; forces status='candidate' (an alternate is never independently committed); inherits the target's day_id and slot unless explicitly given. Reject --alternate-for pointing at another alternate (one level only).
  • plan show: render an alternate inline under its primary as ↩ alt: «title».

4.2 day shuffle

trip-planning day shuffle --date 2026-08-15 --drop <itemId> [--commit] [--by <memberId>]
  • Semantics: mark the dropped committed item rejected; if it has an alternate, promote that alternate to committed in the same slot; then run checkPlan and print (a) the day's new board and (b) that day's errors/warnings only.
  • Dry-run by default. Implementation: BEGIN → apply → compute board + feasibility → ROLLBACK unless --commit, in which case COMMIT and journal two entries (item.reject, item.promote_alternate) with --by as actor.
  • Dropping an item with no alternate is legal — the day simply compacts; say so in the output ("no alternate stored — slot now open").
  • Errors: date has no committed day → exit 1 with message; item not on that date or not committed → exit 1.

4.3 Instruction edit

Append to trip-planning/SKILL.md (Building the plan section): "For weather-risky or bookable items, store a plan-B at planning time with --alternate-for. On-trip, when something is dropped ('rained out', 'running late'), run day shuffle --drop first WITHOUT --commit, play the proposed day back to the group, and only re-run with --commit after a yes."

4.4 Tests — new file trip-planning/test/shuffle.test.ts

  1. --alternate-for forces candidate status and inherits day/slot; chained alternate rejected; target must exist.
  2. Dry-run: output contains promoted alternate, DB unchanged after the call (statuses re-read).
  3. --commit: dropped → rejected, alternate → committed, both journal entries present with actor.
  4. Drop without alternate → slot-open message, item rejected on commit.
  5. Promoted alternate that breaks slack (travel_minutes too big) → the printed feasibility block contains the day's error.
  6. Bad date / non-committed item → exit code 1, no mutation.

§5 Itemised splits trip-finance

Why: the OCR eval fixtures already include itemised bills (eval/fixtures/synthetic/clean/bill-itemised-*.png) but the ledger only stores a total + one rule. "Raj didn't drink — split the beer separately" is the single most common real-world split correction.

5.1 Design decision (load-bearing)

Items are stored for audit/display, but expense_shares remains the only thing balances read. Itemisation is a new way to compute shares, aggregated per member at log time. Balances, settle, void, journal are untouched downstream — this is what keeps the golden tests green.

5.2 Schema + CLI

CREATE TABLE IF NOT EXISTS expense_items (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  expense_id INTEGER NOT NULL REFERENCES expenses(id),
  label TEXT NOT NULL,
  amount INTEGER NOT NULL,            -- minor units
  participants_json TEXT NOT NULL     -- "[2,3]" or "\"all\""
);
$TF log --desc "Dinner" --amount 4500 --payer 5 --by 2 \
   --items '[{"label":"Beer","amount":600,"members":[2,5]},
             {"label":"Food","amount":3900,"members":"all"}]'
  • Item amounts are major units in the expense currency (same convention as --amount); converted with the same parser.
  • Validation (all → exit 1, nothing written): items must be a non-empty array; Σ item amounts must equal --amount exactly (message states both sums); every member id must resolve to an active member at logged_at (reuse activeMembers); "all" means activeParticipants at logged_at; an item's member list may not be empty. --items is mutually exclusive with --rule/--custom.
  • Computation: per item, equal split among its members using the same largest-remainder rounding already in split.ts (call the existing function — do not re-implement). Aggregate per member across items → write expense_shares. Store split_rule='itemised' and the normalized items (minor units, resolved member ids) in custom_spec; also insert the expense_items rows.
  • $TF expense <id>: when itemised, print each item line (label · amount · members) then the per-member aggregate. --json includes an items array.
  • $TF edit <id> --items '…': full replacement — validate, delete old expense_items, recompute shares, journal before/after (existing edit journaling pattern). Editing --amount alone on an itemised expense → exit 1 telling the user to re-supply --items (the invariant Σitems = total must hold).
  • void unchanged (shares ignored when voided already handles it).

5.3 Instruction edits

SKILL.md "Logging an expense": add the flag to the command block, plus: "When a bill photo is itemised and someone asks to split it unevenly ('Raj skipped the drinks'), build --items: read line items from the image, group them, and play back per-person amounts before committing — the itemised playback must show each item group and who's in it." Add a matching line to the image-handling section: itemised bill + uneven-split request → --source bill-image + --items.

5.4 Tests — new file trip-finance/test/itemised.test.ts

  1. Sum mismatch → exit 1, no expense row, no items rows.
  2. Two items (one "all", one subset) → expense_shares aggregate equals the total exactly; the excluded member's share comes only from the "all" item.
  3. Rounding property (mirror properties.test.ts style): for 200 random itemisations, Σ shares = total, and per-item rounding matches split.ts equal-split output.
  4. --items + --rule → exit 1. Empty member list → exit 1. Unknown member id → exit 1. Member who joined after logged_at → exit 1.
  5. expense <id> human + --json output includes items; balances over a mixed ledger (plain + itemised) settle to zero net.
  6. Edit-replace recomputes; edit --amount without --items on an itemised row → exit 1; void hides it from balances.
  7. Regression: full existing finance suite passes (golden + characterization + properties).

§6 Budget burn trip-finance

Why: planning owns the budget cap; finance owns actuals; they never meet. burn is the join — and the evening/post-trip heartbeat's best content.

6.1 CLI

$TF burn [--at <ISO>] [--json]

Reads trip.start_date / end_date / total_budget / base_currency and active expenses. Output fields:

  • tripDays (end−start in days, inclusive of start), daysElapsed (clamped to [0, tripDays]; day counting starts at 1 on start_date), timePct.
  • spent: per-currency totals of active expenses (minor + formatted).
  • When total_budget is set: baseSpent (base-currency expenses only), budgetPct, remaining; foreign-currency spend listed separately with an explicit note that it is not converted (house rule: never convert silently). When budget is NULL: report spend only, budget: null.
  • dailyRate = baseSpent / max(1, daysElapsed); projection = dailyRate × tripDays; projectionOver flag when projection > budget.
  • topExpenses: top 3 active by amount {desc, formatted, payerName}.
  • Human output is one compact block, e.g. Day 3/5 (60% time) · spent ₹34,200 of ₹50,000 (68%) · pace ₹11,400/day → projects ₹57,000 (OVER by ₹7,000).

Edge rules: before start_date → daysElapsed 0, no projection; after end_date → daysElapsed = tripDays, projection = actual; missing trip dates → spend-only mode with data.reason. Wire burn's JSON into the heartbeat evening + settlement editions as an extra section burn (import the module, don't shell out).

6.2 Instruction edit

SKILL.md, after the balance block: "For 'how are we doing on budget' / mid-trip money questions, run $TF burn and relay its line — never estimate pace or projection yourself."

6.3 Tests — new file trip-finance/test/burn.test.ts

  1. Known fixture (5-day trip, budget 50,000.00, expenses on days 1–3 incl. one voided, one foreign-currency) → exact daysElapsed/timePct/baseSpent/budgetPct/dailyRate/projection numbers; foreign spend excluded from baseSpent and listed separately.
  2. --at before start → no projection; after end → projection = actual; no budget → budget:null; no dates → reason string, exit 0.
  3. topExpenses ordering and tie stability (by amount desc, then id asc).

§8 Person-level memory export/import trip-memory

Why: memory is per-trip (memory.db per group) but "Bob's pace" is true on every trip. Smallest thing that compounds: a portable export keyed on a person, and a provenance-preserving import into the next trip's store. (The operator/agent moves the file between group workspaces; no cross-group plumbing.)

8.1 CLI (extend trip-memory/scripts/trip-memory.ts, following its existing storage layer)

$TM export-person --person "Bob" --out /workspace/agent/exports/bob-memories.json
$TM import --file <path> --trip <id> --by "<sender>"
  • export-person: all active memories whose tags include the person's name (tags already carry member names per the remember convention). Output JSON: {version:1, person, exportedAt, memories:[{title, content, category, tags, importance, provenance, createdAt}]}. Empty result → exit 0, memories:[].
  • import: inserts each as provenance auto (never owner-approved — the new trip's owner re-curates), re-tagged with trip:<id> + imported and stripped of the old trip:* tag. Dedupe: skip when an active memory with identical title+content already exists; report imported N, skipped M. Each import journals/echoes the same MEMORY SAVED receipt lines the store already emits.

8.2 Instruction edit

SKILL.md, new short section "Carrying memory to the next trip": "When a new trip starts with returning travellers, offer once: export each returning person's memories from the old trip's store and import here; everything arrives as unapproved (auto) and the owner prunes with approve/forget. Never import without telling the group what came over."

8.3 Tests — extend trip-memory/test/cli.test.ts

  1. Roundtrip: remember 3 (2 tagged Bob, 1 not) → export-person Bob has exactly 2 → import into a fresh DB → both present, provenance auto, tags contain imported + new trip:<id>, old trip tag gone.
  2. Dedupe: import twice → second reports skipped 2, no duplicate rows.
  3. Rejected/forgotten memories are not exported. Malformed file / wrong version → exit 1, nothing written.

§9 Vendor-chase payloads from the DB trip-workflows

Why: vendor payload --missing "…" is hand-typed today, but the plan already knows which booking fields are empty.

  • ensureColumn(db, 'stays', 'ref', 'ref TEXT') (legs already have ref), and add --ref to stay add/a stay field-setter in trip-planning.
  • New flags on vendor payload: --db <path> --from stays:<id> (or legs:<id>). Derivation table: ref NULL → "confirmation number"; stays check_in NULL → "check-in time"; legs depart/arrive NULL → "departure/arrival time"; booking_url NULL → "booking link/receipt". Derived list is printed and still overridable by an explicit --missing. Row not found or nothing missing → exit 1 with a clear message ("nothing to chase — all fields present").
  • Tests (extend trip-workflows/test/trip-workflows.test.ts): stay with NULL ref+check_in derives both phrases; fully-populated row → exit 1; explicit --missing wins; legs variant.
